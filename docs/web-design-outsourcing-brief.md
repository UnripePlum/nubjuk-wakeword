# Custom Wakeword Web Studio Design Brief

Purpose: design outsourcing scope document.

This document lists only the pages, flows, and functional UI requirements needed for design work. It does not define visual style, branding, color, typography, or implementation details.

## Product Summary

The product is a local web studio for creating a custom TinyML wakeword model.

The user enters the wakeword they want, reviews similar-sounding words, generates and listens to one sample, then proceeds through data generation, training, evaluation, export, and host microphone testing.

Primary user:

- A hardware or embedded product builder who wants a custom wakeword.
- They may understand ESP32/MCU products, but should not need to understand ML pipeline details.

Primary goal:

- Let the user create a deployable wakeword model package for their own wakeword.

## Core User Flow

```text
1. Create or resume run
2. Enter wakeword
3. Review suitability
4. Review near-miss words
5. Generate one seed sample
6. Listen and approve/reject seed sample
7. Choose data generation plan
8. Generate and clean training data
9. Train model with progress view
10. Review evaluation and threshold
11. Export MCU package
12. Run host microphone test
```

## Global UI Elements

These should appear across the app where relevant.

### Stage Navigation

Shows the user's current step in the wakeword creation flow.

Required stages:

1. Wakeword setup
2. Near-miss review
3. Seed sample
4. Data plan
5. Data generation
6. Training
7. Evaluation
8. Export
9. Host mic test

Required behavior:

- Show current stage.
- Show completed stages.
- Show locked future stages.
- Allow navigating back to completed stages when safe.

### Run Context Panel

Shows persistent run information.

Required fields:

- Wakeword text
- Language
- Slug
- Model name
- Current stage
- Last error, if any
- Created time
- Updated time

### Event Timeline

Shows progress for long-running jobs.

Required content:

- Current job status
- Recent progress events
- Error message if failed
- Retry action when available
- Collapsed raw log area for debugging

### Artifact Panel

Shows files generated by the run.

Required artifact types:

- Seed WAV
- QC manifest
- Generated sample directory
- Training logs
- Evaluation plots
- Exported TFLite model
- Export manifest JSON

## Pages And Screens

### 1. Home / Run List

Purpose:

- Start a new wakeword run or resume an existing one.

Required UI:

- New run call-to-action
- Recent runs list
- Run status badge
- Wakeword text
- Last updated time
- Continue button
- Delete/archive action, optional

Empty state:

- Explain that no runs exist yet.
- Primary action: create first wakeword.

### 2. Wakeword Setup Page

Purpose:

- Let the user define the wakeword and basic metadata.

Required inputs:

- Wakeword text
- Language
- Pronunciation hint
- Optional model/package name

Required outputs:

- Generated slug
- Generated model name
- Suitability result
- Warnings if the wakeword is risky

Required actions:

- Create run
- Save changes
- Continue to near-miss review

Error states:

- Empty wakeword
- Unsupported characters
- Wakeword too short
- Slug collision

### 3. Near-Miss Review Page

Purpose:

- Let the user approve words that sound similar to the wakeword.

Required UI:

- Suggested near-miss list
- Approved near-miss list
- Add custom word input
- Remove item action
- Reorder action, optional
- Approved count
- Explanation of why near-miss words matter

Required actions:

- Add word
- Remove word
- Save approved list
- Continue to seed sample generation

Error states:

- No approved near-miss words
- Duplicate word
- Candidate generation failed

### 4. Seed Sample Page

Purpose:

- Generate exactly one sample before bulk data generation.

Required UI:

- Generate seed sample button
- Progress state while generating
- Audio player for generated sample
- QC summary
- Seed artifact links

Required actions:

- Generate
- Play audio
- Approve sample
- Reject sample
- Regenerate sample
- Go back to edit wakeword or pronunciation hint

Required states:

- Not generated
- Generating
- QC passed
- QC failed
- User approved
- User rejected

### 5. Data Plan Page

Purpose:

- Show what will be generated before running bulk data generation.

Required UI:

- Preset selector
- Prototype preset
- Balanced preset
- Higher quality preset
- Positive sample count
- Near-miss/adversarial sample count
- Background negative source summary
- Output directory summary
- Advanced settings collapsed by default

Required actions:

- Select preset
- Review generated plan
- Start data generation
- Back to seed sample

### 6. Data Generation And QC Page

Purpose:

- Show progress while generating and cleaning training audio.

Required UI:

- Generated count
- QC passed count
- QC rejected count
- Rejection reason breakdown
- Playable sample grid
- Failed sample examples, optional
- Current job progress

Required actions:

- Start generation
- Pause/cancel, optional
- Retry failed generation
- Continue to feature preparation/training

Required rejection reasons:

- Too short
- Too long
- Low volume
- Clipping
- Corrupt audio
- Wrong sample rate

### 7. Training Page

Purpose:

- Show model training progress without requiring terminal logs.

Required UI:

- Current step
- Total steps
- Training status
- Latest validation loss
- Latest validation accuracy or recall
- Training curve link or preview
- Validation curve link or preview
- Recent log tail
- Error panel if failed

Required actions:

- Start training
- Cancel, optional
- Retry
- Continue to evaluation

Required states:

- Waiting for data
- Preparing features
- Training
- Completed
- Failed

### 8. Evaluation And Threshold Page

Purpose:

- Let the user understand model quality and choose an operating threshold.

Required UI:

- Recommended threshold
- Threshold slider or selector
- False reject summary
- False wake summary
- Precision/recall summary
- ROC/PR chart preview
- Score distribution chart preview
- Plain-language tradeoff explanation

Required actions:

- Accept recommended threshold
- Adjust threshold
- Save threshold
- Re-run evaluation
- Continue to export

Plain-language framing:

- More sensitive: fewer missed wakes, more false wakes.
- More strict: fewer false wakes, more missed wakes.

### 9. Export Package Page

Purpose:

- Produce and show the files needed for MCU integration.

Required UI:

- Export status
- Exported `.tflite` file
- Exported `.json` manifest
- Wakeword text
- Language
- Probability cutoff
- Sliding window size
- Feature step size
- Tensor arena size
- Download/copy file actions

Required actions:

- Export package
- Download files
- Copy paths
- Continue to host mic test

Required warnings:

- Export package is ready for MCU integration.
- Host mic behavior may differ from MCU behavior.

### 10. MCU Handoff Page

Purpose:

- Give the user a clear checklist for using the exported model on device.

Required UI:

- Required files checklist
- Manifest values checklist
- Firmware integration checklist
- On-device validation checklist
- Known limitations

Required content:

- Model file path
- Manifest file path
- Probability cutoff
- Tensor arena size
- Feature step size
- Sliding window size

### 11. Host Microphone Test Page

Purpose:

- Let the user quickly test the model from the local machine microphone.

Required UI:

- Microphone permission state
- Start/stop test button
- Live score display
- Wake detected indicator
- Event log
- Current threshold
- Selected model path

Required warnings:

- This is a host mic test.
- It is useful for quick sanity checks.
- It does not guarantee MCU behavior.

Required states:

- Waiting for model
- Waiting for microphone permission
- Listening
- Wake detected
- Error
- Stopped

### 12. Settings / Advanced Page

Purpose:

- Keep advanced controls out of the main flow.

Required UI:

- Default sample counts
- Qwen model/device settings
- QC thresholds
- Training step defaults
- Negative dataset paths
- Artifact storage location
- Reset defaults action

Required behavior:

- Advanced settings should not be required for normal users.
- Dangerous or expert-only settings should be clearly separated.

## Required Empty States

The design should include empty states for:

- No runs yet
- No near-miss candidates
- No approved near-miss words
- No seed sample yet
- No generated data yet
- No training run yet
- No evaluation output yet
- No export package yet
- No microphone permission yet

Each empty state needs:

- Short explanation
- Primary action
- Secondary help text, if needed

## Required Error States

The design should include error states for:

- Invalid wakeword
- Failed near-miss generation
- Failed seed generation
- Seed QC failure
- Data generation failure
- Training failure
- Evaluation failure
- Export failure
- Microphone permission denied
- Missing artifact file

Each error state needs:

- Human-readable cause
- Retry action
- Back/edit action when useful
- Raw detail drawer for debugging

## Responsive Requirements

Desktop:

- Full workbench layout.
- Current task and run context visible side by side.

Tablet:

- Current task first.
- Run context below or collapsible.

Mobile:

- Single-column flow.
- Stage navigation remains visible.
- Primary action remains easy to reach.
- Touch targets should be large enough for mobile use.

## Out Of Scope For Design Vendor

Do not design these unless separately requested:

- Public marketing website
- Account/login system
- Team collaboration
- Cloud hosting dashboard
- Billing/pricing
- ESP32 flashing tool
- Full device management console
- Multi-run experiment comparison
